Localino Live - implementation of LocalinoRemoteApi via Localino REST API (https://api.localino.app).

## Features

Loads localization asset based on current or preferred locale.\
Formatted as Json/Map. Handles single strings, maps and lists, plurals and simple formatting.\

## Getting started

Add library to your pubspec.yaml under dev_dependencies.

```yaml
dev_dependencies:
  build_runner: 2.4.0
  localino_builder: 0.1.0
```

Add `build.yaml` to your project files to configure builder and localino project.

```yaml
targets:
  $default:
    builders:
      localino_builder:
        options:
          space: 'your space id'
          project: 'your project id'
          access: 'your access token'
```


## Usage

Just run `build_runner` to download your translations into assets folder.

```
dart run build_runner build
```

## Typed key generation (opt-in)

Beyond downloading JSON, the builder can emit a Dart file of typed key
constants so call sites get compile-time safety, autocomplete, and hover docs
instead of raw magic strings.

Enable it with the `generate_keys` option:

```yaml
targets:
  $default:
    builders:
      localino_builder:
        options:
          space: 'your space id'
          project: 'your project id'
          access: 'your access token'
          generate_keys: true    # default false — opt-in, non-breaking
          report_unused: true     # optional — list keys with no LocalinoKeys.* ref
```

Generation runs on the **standalone** path the package already uses to download
JSON — it is not a `build_runner build` source builder. Trigger it directly:

```
dart run localino_builder --generate-keys --report-unused
```

Output is written to `lib/generated/localino_keys.dart`:

```dart
// GENERATED by localino_builder — do not edit by hand.
abstract final class LocalinoKeys {
  /// Add
  static const action_add = 'action_add';

  /// Version: {version} ({number})
  /// params: version, number
  static const version = 'version';

  /// Delete locale
  /// ⚠ missing in: cs_CZ
  static const action_delete_locale = 'action_delete_locale';
}
```

Call sites become:

```dart
title: Localize.i(LocalinoKeys.action_add),
```

The const **value** is always the original JSON key verbatim — runtime lookups
are unchanged. Doc comments show a default-locale preview, `params:` for format
strings, and a `⚠ missing in:` note for keys absent in other locales.

With `report_unused: true`, after generation any key with no
`LocalinoKeys.<name>` reference under `lib/` is printed (report-only, never
deleted) — useful for pruning dead keys once call sites are migrated.

## Sync (two-way)

The plain download above overwrites local locale files. The sync commands
instead merge local files and Localino key by key, so translations can be
edited in either place:

```
dart run localino_builder status            # what changed where
dart run localino_builder pull [--dry-run]  # apply Localino changes locally
dart run localino_builder push [--dry-run]  # send local changes to Localino
dart run localino_builder sync              # pull, then push
```

Config comes from `build.yaml` options or, if the builder is missing or
`enabled: false` there, from `assets/localization/setup.json` (`space`,
`project`, `access`, `asset`). Use `--root <dir>` to point at a project; by
default the nearest `pubspec.yaml` above the working directory is used.

### Lock file

`.localino/lock.json` records, per locale and key, a hash of the last synced
value and its Localino timestamp. **Commit it** — it is the shared baseline
that tells a local edit from a translator's edit. Each key is classified by
comparing local, lock and remote values:

| Local vs lock | Remote vs lock | State | pull | push |
|---|---|---|---|---|
| same | same | unchanged | — | — |
| changed | same | local changed | kept | sent |
| same | changed | remote changed | applied | — |
| changed | changed, equal to local | converged | lock updated | — |
| changed | changed, different | **conflict** | stops | stops |

Deleting counts as a change, so deleting a key on one side while editing it
on the other is a conflict. Without a lock (first adoption) equal values
become the baseline, one-sided keys are added and different values conflict.

- `pull` never drops keys that only exist locally.
- `push` never deletes keys in Localino unless `--prune` is given.
- A conflict stops the run with nothing written (exit 3). Re-run with
  `--prefer local` or `--prefer remote` to pick a side.
- A local value whose type differs from the key's type in Localino (e.g. a
  plural map where Localino has text) also stops the run before anything is
  written (exit 3). Push never changes a key's type: change or delete the key
  in the Localino console, then re-run.
- Existing key order and indentation are kept; new keys are appended sorted.
- When `generate_keys` is on, `pull` regenerates `lib/generated/localino_keys.dart`.
  Any other localization codegen of your project still has to run afterwards.

### Write key

`push` and `sync` need a per-project **write key** (`lk_w_…`), generated in the
Localino console. The `access` read token is never accepted for writes. Store
the key once per machine — it is read from stdin, so it stays out of shell
history:

```
dart run localino_builder login
```

It is saved to `~/.localino/credentials.json` (mode 600), keyed by
`space/project`. In CI set `LOCALINO_WRITE_KEY` instead. Never commit the key.

`LOCALINO_API_URL` overrides the API base (default
`https://api.localino.app/v1`); only https is accepted, plain http only for
`localhost`.

### Exit codes

| Code | Meaning |
|---|---|
| 0 | OK |
| 1 | Usage or other error |
| 3 | Conflict (incl. a value type change) — nothing written |
| 4 | Missing, malformed or rejected credentials |
| 5 | Network failure or concurrent push — re-run |

`sync` that pulled but failed to push keeps the pull applied and exits with
the push's code — 5 (network, contention) means re-run `sync` to finish.
Network failures never touch local files.

## MCP server (coding agents)

`dart run localino_builder:mcp` is a local stdio [MCP](https://modelcontextprotocol.io)
server over the same sync engine, so a coding agent can find, add and sync
keys without the console. Register it in the project's `.mcp.json`:

```json
{
  "mcpServers": {
    "localino": { "command": "dart", "args": ["run", "localino_builder:mcp"] }
  }
}
```

(With fvm use `"command": "fvm", "args": ["dart", "run", "localino_builder:mcp"]`.)
The server runs from the project root; pass `--root <dir>` otherwise.

| Tool | Does |
|---|---|
| `localino_status` | Counts and changed keys (local vs lock vs Localino); offline it compares local files with the lock. |
| `localino_search_keys` | Searches local files by key/value substring, exact `keys`, or keys missing in a locale. Flags keys with an identical value so existing keys get reused. |
| `localino_set_keys` | Adds, updates or removes keys in local files only (git-reversible). Rejects unknown locales; regenerates `localino_keys.dart` when `generate_keys` is on. |
| `localino_pull` | Applies Localino changes locally; conflicts stay untouched unless `prefer` is given. |
| `localino_push` | **Dry run by default** — returns the plan. Applies only with `dry_run: false`. Never deletes remote keys (use the CLI `push --prune`). |

Typical agent flow: `localino_search_keys` → `localino_set_keys` → run the
project's localization codegen → `localino_push` (plan) → user confirms →
`localino_push { "dry_run": false }`.

The write key never passes through the agent: the server reads it from
`~/.localino/credentials.json` or `LOCALINO_WRITE_KEY`, no tool accepts it,
and anything shaped like a write key is masked in tool output. Run `login`
yourself in a terminal; never paste the key into a chat.
